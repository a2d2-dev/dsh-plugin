# DSH 实际会话参考：Issue 启动、接替与统一状态展示

## 结论与本轮边界

用户明确旧实现只作参考，其中映射或处理可能存在错误；本轮不据此迁移、修复或固化旧模型。研究目标是理解三个痛点：**从 Issue 直接创建处理会话；会话接替后工作连续；大量子会话及后台工作有统一状态展示。**

结论：这三个能力应围绕同一项工作形成完整链路。Issue 是稳定入口；当前处理会话是可更新的处理位置；接替历史、实施/评审子会话和后台作业属于这项工作的执行记录。用户应能从 Issue 找到当前处理位置、知道目前在做什么和卡在哪里，而不必通过聊天标题、编号后缀或重复提问推断。

## 围绕三个痛点的交互方案

### 1. 从 Issue 直接开始

- Issue 行和详情都提供“开始处理”；点击后沿用项目的执行配置，带入 Issue、当前接受范围及必要父任务背景，创建对应处理会话并直接打开。
- 已有当前处理会话时，入口显示“进入当前会话”。历史失败、暂停、待接替应按实际状态提供继续/恢复入口，不重复创建同一执行。
- 会话标题仍使用 DSH 单标题布局，右侧“关联任务”显示 Issue 和用途，可回到任务详情。普通引用到别的 Issue 不自动改变主责绑定。
- 如果同一系列涉及多个 Issue，归属以明确的任务及关联关系展示，不把所有被提及编号都当本会话负责范围。

### 2. 工作连续，当前会话可以替换

- 用户始终从同一个 Issue 找到当前会话；切换后入口自动指向后继，旧会话保留只读历史。
- 接续页展示当前参数、接替原因、来源段、后继段、具体摘要和下一步。
- 交接过程明确显示“准备接续 → 收取必要结果/旧段收尾 → 后继接任 → 继续工作”；新会话创建成功、READY 和主责已移交分开表达。
- 未结算的子会话、后台作业和待处理输入进入交接清单；根据宿主能力等待收取或明确移交，不能假设关闭主会话就表示整项工作已收口。
- 历史上换到新Issue范围的工作，显示范围变更或新任务关联，不伪装成原任务的普通换段。

### 3. 一处看清整项工作的执行状态

以 **Issue 详情的“会话”页作为统一执行入口**，保留当前四个详情标签，先不增加另一套顶级工作台。可将该页标题标为“会话与执行”：

1. 顶部摘要：当前处理会话、目前在做什么、阻塞/待你处理、最近更新时间。
2. 当前处理：一行突出当前主责，标明运行、等待、暂停或接续中的实际状态。
3. 协作执行：按工作/用途列出实施、评审、验收等子会话，可显示对应子 Issue、结果与需要收取的事项。
4. 后台工作：显示相关执行者所属的作业、检查或等待事件，注明 owner 和结果；不是只列当前主会话自己的 job 表。
5. 历史：接替段次与重试尝试默认折叠，保留来源、结果及被谁接替/覆盖，不让已处理的失败反复占据“需要关注”。

建议表格字段：

| 工作 / Issue | 用途 | 会话或作业 | 当前状态 | 最近结果 / 待办 | 操作 |
|---|---|---|---|---|---|
| 当前任务 | 负责协调 | 当前处理会话 | 处理中 / 等待 / 接续中 | 当前下一步 | 进入会话 |
| 子任务或独立工作块 | 实施 | 子会话 | 运行中 / 失败 / 已返回 | 产物、失败原因、待复核 | 打开会话 |
| 同一任务 | 评审 | 评审会话 | 运行中 / 已返回 | 审查范围与结论 | 查看结果 |
| 某执行者的工作 | 后台作业 | Job / CI引用 | 运行中 / 已结束 / 待收取 | 退出结果与后续动作 | 查看详情 |
| 同一任务 | 接替历史 | 历史处理会话 | 已接替 | 交接摘要、后继 | 查看历史 |

这里应同时回答“执行现在怎么样”和“业务还剩什么”。宿主结束状态、子会话返回、PR合并、本地验收完成分别展示；不能只用绿色“已完成”概括所有层次。

DSH 原生子智能体/后台任务面板仍用于查看某个会话的执行细节；A²D² 负责把这些信息按 Issue 汇总，并串起跨段历史。这样直接补上用户关心的统一观察面，不要求用户换一套聊天方式。

## 后续原型落点

现有 Issue 创建会话、标题关联入口、接续 Tab 可以沿用。下一步重点是完善 Issue 详情的“会话”页：加入当前处理摘要、协作会话和后台工作、折叠接替及重试历史。演示素材可使用 #3342 真实拆分配合上述接替/协作场景，但真实GitHub数据、历史DSH观察和模拟运行状态必须明确区分。
