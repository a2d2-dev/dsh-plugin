# 对话执行护栏

## 背景

#309 记录了一个具体失败：任务尚未完成，用户追问状态，模型承认自己误设等待，却仍要求用户再说“继续”。旧动态提示无条件强调“人工对话不恢复自动调度”“等待后结束本轮”，没有说明模型如何纠正自身错误。#312 优先修复这条对话路径与不必要的术语。

## 目标与范围

活动任务收到状态询问后简答并继续原授权内的工作；模型自己的错误等待可以核实、纠正。用户暂停、停止、只回答及真实阻塞保留。缺少可自行读取的证据不能直接当成外部阻塞。

只作用于现有 WorkApplication 当前处理会话，不接管普通会话或历史会话，不增加另一套 Task 状态机，不创建 Goal，不修改 DSH 核心，不把 Full access 当成额外业务授权。新增设置页与会话页签不在本次范围。

## 架构

DSH adapter 观察实际人工输入、工具结果和准备结束的轮次。WorkApplication 依据当前执行与控制记录判断是否需要纠正。纠正经公开 `agent.steer()` 加入同一轮，不用浏览器轮询或额外模型调度器。

| 位置 | 职责 | 数据归属 |
| --- | --- | --- |
| `work-execution/dsh-host.ts` | 接收公开事件、识别当前人工意图、观察真实工具结果、投递纠正提示 | DSH 会话日志 |
| `work-execution/guard.ts` | 输入与等待协议、简洁行动指令 | 无独立存储 |
| `work.ts` | 核对当前任务范围、等待来源、运行条件和纠正次数 | 原 Work DAO 的 Execution |
| `work-execution/tools.ts` | 既有 `work_control wait` 接收具体等待原因与恢复条件 | 原 Execution.control |
| `work-organization-tools.ts` | 沿用 `work_related_issue` 读取已接受的依赖 | 原来源观察记录 |

输入经过当前会话授权检查后进入 DSH；若模型仅解释或更新状态便准备结束，护栏判断是否还能推进。默认最多纠正两次；重复结果与单纯记账不能不断补充次数。到达上限后保留具体运行问题与未完成状态，不能谎报完成。

恢复提示只随下一次已获准的输入注入。打开或恢复会话对象本身不启动工作。工具调用和材料可以写入诊断记录，但用户回复只需说明结果、动作和具体阻塞。

## 使用与验证

### 接入

按仓库既有流程构建和安装插件：

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm pack --pack-destination .local/release
```

使用 DSH 当前 profile 的插件管理入口安装生成的包，并按实例已有方式重启。旧会话对象需重新加载才能使用新的回调。`a2d2-work` 插件配置支持 `executionGuard` 与 `guardMaxCorrections`；默认启用、两次，关闭不改变任务授权。查看页面不会自行恢复任务。

### 状态追问与模型误设等待

在当前处理会话发送“没看懂，现在需要我做什么呢？”或“到底是什么状态”。若原任务仍有可执行工作，应出现简短回复和真实工具动作。模型自行设置的旧等待先核查依赖，再通过既有 `work_control resume` 纠正；仅显示“已接受”或“将继续”不是通过。

数据走向：人工消息 → DSH `agent/pre-step` → 当前任务上下文 → 模型与工具 → `agent/turn-stopping` → 必要时同轮纠正。用正式日志中的工具调用、成功结果和实际产物确认，而非只看回复文案。

### 真实等待与用户停止

模型使用 `work_control wait` 时提供 `yield_reason`、`checked_facts`、`wake_condition`。`internal` 表示仍可自行检查，会返回行动提示；`human` 或 `external` 说明缺什么和何时恢复；`executor` 需要能核实的准确子会话或作业。旧记录仍可读取，不能因为升级就批量解除等待。

发送“只回答当前状态，不要继续执行”，应得到回答且不被护栏追加执行。人工暂停、已结束队列、已完成任务和交接维护同样不被纠正成业务执行。

### 自动输入排在人工消息之前（#315）

会话对话与 Task 当前主会话归属分别判断。本轮仅修复人工消息被队首自动输入挡住的路径，保留所有自动输入原有准入、路由和控制；不让 schedule、结果或其他自动来源自行进入等待会话，不自动恢复任务，也不重新决定数据路由。

真实 DSH Inbox 每轮只领取一条 next-turn；pre-step 拒绝队首自动消息会停止整个驱动。adapter 在原准入拒绝后，使用公开 Inbox.remove 将已有 source.kind=user 的完整人工消息按原顺序送入本次对话。被拒自动输入沿用原 Task 事件或宿主生产者恢复路径，不混入人工模型请求。人工消息不改变 wait/pause/end、owner/epoch、完成事实、持续槽位或准确维护范围。没有新增定时器、Goal 或统一宿主工具限制。

回归使用真实 Agent loop、durable Inbox 和 JSONL：两条自动消息前置、两条人工消息后置，在 waiting/paused 时人工各消费一次、自动保持原控制且原载荷保留；退役和已完成会话仍可回应人工，但 Task 修改和恢复被拒绝。重复恢复检查不新增空轮或重复投递。

### 无进展上限

反复纯文本结束、只更新状态或重复读取相同结果，不能无限续跑。达到上限后查询 `task.execution` 可见 `executionGuard` 与具体控制原因；任务验收仍为未完成。新进展必须来自实际结果，不能通过新一轮、重载插件或改写进度文字重置限制。

回归入口：

```sh
pnpm exec vitest run tests/work-execution-guard.spec.ts tests/work-execution.spec.ts
```

真实供应商验收与确定性回归分开记录。该机制能纠正可观察的停顿，并不声称能证明任意工具动作都有业务价值，也不保证所有自然语言暂停表达均能由模式识别覆盖。
