# 任务交互 v4：观察与待验证方案

对应交付：[打开 v4 原型](task-interaction-v4-dsh.prototype.html) · [体验说明与模拟边界](task-interaction-v4-dsh.README.md)。

本记录先保存观察与用户已确认的方向，供下一版原型验证。**v4 只是原型迭代号，领域仍沿当前 v3**，不引入新的领域版本。以下方案尚待原型验证，不表示已经实现。

来源：[DSH 会话连续性研究](../architecture/dsh-session-continuity-review.md)、[Project14 真实工作结构研究](../architecture/project14-imneov-integration-review.md)。这些是已有研究记录，本轮只读两份文档，未重新读取真实会话或远端状态。界面约束及三个目标来自用户本轮确认。

## 一、真实观察

- **Issue 树不等于会话树。** [#3342](https://github.com/theriseunion/freeland/issues/3342) 汇总四张独立子单，子单保留各自负责人、规格和验收；其中 #2979 由其他负责人处理。历史 #2995 的首段是独立根会话，后续接替段在宿主上却是同一会话的直接子会话。业务父子、原生会话父子和接替关系不能混为一谈。[结构证据](../architecture/project14-imneov-integration-review.md#L55)、[会话证据](../architecture/dsh-session-continuity-review.md#L42)
- **同名可以对应多段工作；准备接替不等于已经接任。** 三个历史会话标题完全相同，但范围和主责发生变化，不能按标题、后缀或时间自动串成同一 Issue 的段次。#2995 的接替链有交接消息与任务记录印证；后继 READY 时，当前绑定仍可能留在旧段，正式移交才是接任依据。[同名记录](../architecture/dsh-session-continuity-review.md#L21)、[准备与生效证据](../architecture/dsh-session-continuity-review.md#L50)
- **并行评审与失败后的继续处理都存在。** 同一产物可以同时收到不同职责的评审结论，互不替代，也不是前后接替。#3031 的多个子会话最后一轮因服务错误结束，主会话仍继续推进并记录任务完成；重试/继续的历史不能直接解释为当前阻塞。某轮 completed 也不等于业务验收完成。[评审与失败记录](../architecture/dsh-session-continuity-review.md#L69)
- **后台工作有自己的执行归属，历史证据需要跨段保留。** 主会话没有后台 job，不代表子执行者没有作业、未收取结果或待处理产物。接替涉及既有执行者、输入和未提交成果；不能因切换当前会话就丢失这些信息。[交接证据](../architecture/dsh-session-continuity-review.md#L65)
- **真实工作状态本来就有多个来源。** Issue 开闭、Project 状态、会话运行结果、PR 合并和验收证据可能不同步；旧正文和历史关系也可能已被后续范围裁定更新。[状态组合](../architecture/project14-imneov-integration-review.md#L43)、[范围变更](../architecture/project14-imneov-integration-review.md#L102)

上述旧映射、历史错误和研究中的建议只作参考，不固化为新规则。真实结构取自已有研究快照，不宣称是当前实时状态；历史会话证据不构成新本地会话绑定。

## 二、用户确认的三个目标

1. **Issue 直接创建对应会话。** 从任务进入处理，明确处理对象与范围，减少手动建立关联。
2. **接替。** 同一项工作能够连续推进，用户能辨认当前处理会话、接替准备与正式接任，并保留历史。
3. **统一状态。** 一处看清当前处理、协作会话、后台工作和历史结果，知道在做什么、卡在哪里、还剩什么；统一展示不意味着抹平不同来源状态。

这些目标已确认；下节的具体组织方式仍是本版待验证方案。

## 三、本版待验证的交互方案

- 以 [#3342](https://github.com/theriseunion/freeland/issues/3342) 的真实父子结构作为主要场景。Issue 提供创建对应会话与进入当前会话的路径；父协调、子独立处理的范围和关系需能辨认，不从任务树机械生成会话树。
- 在 Issue 详情的会话区域集中展示当前处理、协作执行、后台工作与历史。协作项显示用途，后台项显示所属执行者；接替与重试历史保留来源、结果和后续处理，避免把已处理错误继续显示为当前告警。
- 接续展示尝试区分“准备接续、必要结果收取/旧段收尾、后继接任、继续工作”；当前入口随正式接任切换。具体状态表达及操作节奏交由本轮原型验证，不把历史实现当成领域契约。
- 明确区分 **真实 Issue 结构、历史 DSH 观察、模拟执行**。未经核验的真实 Issue 不显示已存在新本地会话；需要演示创建、评审、失败重试或接替时，清晰标注模拟执行及模拟结果。

本版必须保留用户已经确认的界面约束：

- DSH 保持单标题；标题右侧为“关联任务”紧凑浮层；标题下保留“对话 / 轨迹 / 接续”Tab。
- 上下文归悬浮球承载。
- Issue 详情的自动接续设置只留顶部一处，参数可直接看。
- 项目持续处理入口放表格头右侧，来源信息归左侧，不显示读取主机。
- 全局演示抽屉覆盖左右区域，悬浮球位于抽屉上方。
- 不做浏览器走查；根据用户反馈快速修改。

## 四、补充确认：GitHub Project 与仓库两种来源

用户进一步明确：添加时可以直接粘贴 GitHub Project 链接，也可以粘贴一个仓库链接。Project 来源展示看板收录的 Issue 和相关 PR；仓库来源展示该仓库的 Issue 和 PR，不以用户使用 GitHub Project 为前提。两种来源都作为顶栏项目标签，末尾“＋”统一添加；依据链接自动识别，无需先选择类型。

这项补充改变来源范围的表达，不将来源类型等同于任务或会话身份。同一 Issue 从不同入口出现时，已有处理会话应继续复用。

## 五、补充确认：持续处理是自然语言委托

持续处理入口以一段用户原话表达目标、范围和边界，交由提示词模板结合当前来源、Issue 内容、已有会话及最新进展理解。用户不需要填写负责人/里程碑等规则表，也不承担逐项排队的工作。

AI 的判断必须可观察：先展示排好顺序的 Issue 列表，以及每项准备做什么、为什么先做、继续已有会话还是新建会话。当前先验证这种展示；不提供手动上移、下移或移出计划。用户通过自然语言补充和纠偏。

单独保留 Block 名单，表达哪些 Issue 不应再接入，后续 AI 重新安排时继续遵守。Block 是明确排除边界，不等于人工排序；已在途工作保留必要收尾，不声称点 Block 就撤销已有动作。

当前 HTML 使用固定示例模拟安排，明确未调用模型解释任意条件；不能把示例排序或本地调度简化宣称为真实 AI 决策。

本记录只整理观察与验证边界；原型的已实现交互与模拟范围见对应体验说明。
