# Issue 驱动与会话执行 · 原型 v4

[打开新原型](task-interaction-v4-dsh.prototype.html) · [观察与设计方向记录](task-interaction-v4-observations.md)

v4 是独立的原型迭代号，领域仍沿当前 v3。旧版 [DSH 控制面板原型](task-interaction-v3-dsh.prototype.html) 保留供对照。

## 这版要验证什么

1. 从 Issue 直接创建对应的处理会话，之后始终能从 Issue 进入当前会话。
2. 会话接替时区分准备、收取结果、正式接任；工作身份、决定和历史继续保留。
3. 在 Issue 的“会话与执行”页统一看到当前处理、子 Issue 的处理入口、协作会话、后台工作、待确认和历史尝试。

## 数据与边界

- 页面自包含，无依赖、无需服务器，直接打开 HTML 即可。
- 内置 2026-10-21 Project14 的 **31 个代表 Issue** 及其父子结构，覆盖 #3342、#2272、#2633、#2104 等场景。视图过滤表达采用读取到的 Project 定义。它不是 Project 全量，也不是实时 GitHub 视图。
- 原始 Issue 说明可在详情中展开，PR 每项最多收录最近两条交叉引用，明确不把引用当验收。
- **处理会话、运行状态、子会话、作业、接续、验收和关闭同步全部为模拟**，与真实 DSH 当前绑定无关。所有状态只在页面内存里，刷新重置。
- 不请求 GitHub/DSH、不调用模型、不启动后台执行。只有用户主动点击 GitHub 外链时才打开对应网页。
- 顶栏采用“A²D² 控制面板 → 项目标签 → ＋”的排列。加号支持粘贴两类来源：GitHub Project 链接，展示其收录的 Issue 与相关 PR；GitHub 仓库链接，直接展示该仓库的 Issue 与 PR，无需 GitHub Project。模拟识别后确认添加并进入；按来源类型与规范身份去重，保留 Project 链接中的视图/切片参数。
- Project 接入后的标签顺序为“概览 / 项目 / Issue / PR”；Repo 接入为“概览 / Issue / PR”。添加或切换来源默认进入概览，汇总开放 Issue、已收录 PR、当前处理、需要关注和最近进展。
- “项目”展示 GitHub Project 的视图与字段；“Issue”独立按分配给我、开放、已关闭、全部筛选；“PR”展示对应范围的记录。仓库不要求 Project 状态或视图。可以添加 `https://github.com/theriseunion/freeland` 体验已有快照；其他未内置来源明确展示说明，不复用别的来源条目。PR 样例仅来自此前已采集的引用，未额外读取仓库全量 PR。
- 从不同来源打开同一 Issue，复用已有工作和处理会话。添加和浏览不启动执行或改变原持续处理规则；开启持续处理时明确记录 Project/仓库范围。
- 纯本地任务创建、完整 GitHub 项目发现目录、生产执行设置不在这版重点范围；原型中的新会话入口引导从 Issue 开始。

## 建议体验顺序

### 1. 先看统一执行

项目页打开 **#3342**，切到 **会话与执行**：

- 父任务的当前负责会话单独显示。
- #3270、#3025、#3026 各有自己的处理入口；#2979 保留 wuxs 负责人背景。
- #3270 的实施、评审和后台检查统一可见；#3025 的待确认问题可直接回复。
- 旧失败尝试放在折叠历史中，不占当前阻塞。

### 2. 从 Issue 开始

打开 **#3026** → **开始处理**。进入新建的对应会话；从标题右侧“关联任务”可回到详情或统一执行页。再次开始/进入复用同一个处理入口。

### 3. 看参数和会话接替

Issue 详情顶部保留唯一的 **自动接续** 设置按钮。**Issue 详情与 DSH 会话窗口都提供“接续”标签**，参数无需打开编辑弹窗就能查看。

展开底部全局 **原型演示**，选择 **会话接替** 场景，按顺序点击：

1. 准备接续：创建待接任后继，当前入口仍指向第2段。
2. 执行结果返回：在途实施和检查结束，结果尚待收取。
3. 收取结果：进入可接替状态；未开始的评审待办保留。
4. 接替并继续：第3段正式接任，原段成为历史，Issue入口随之更新。

也可以在初始 #3270 注入 **上下文 +30K**，由184K越过200K，触发自动准备；结果收齐后自动接任。模拟“后继准备失败”后，原会话不失去当前入口，重试复用本次后继。

### 4. 看确认与重试

- **确认与保留** 场景：回复 #3025 的具体决定，再准备接续并接任，检查新段摘要中的决定。
- **失败与重试** 场景：模拟 #3270 实施失败，在协作行点击“沿原范围重试”。旧执行与旧检查进入历史，新尝试单独显示。

### 5. 看持续处理

项目表格头右侧打开 **持续处理**，用一段话描述希望持续推进的工作。用户原话会与当前来源、Issue/会话进展、Block 名单一起装配进提示词模板，目标是由 AI 给出具体安排。

原型先展示 **排好顺序的 Issue 列表**，每项含纳入原因、下一步、已有会话或新建会话。列表没有上移、下移、拖拽排序或“移出计划”。用户通过补充自然语言改变意图；单独的 **Block 名单** 表达不应再接入的 Issue，后续安排保留这一边界，可解除 Block。

当前使用 #3342 系列的固定模拟安排，页面明确说明未调用模型理解任意文字。查看安排不会启动执行；点击开始后按展示顺序模拟推进。遇到等待项保留原会话；Block 不会强行终止已经运行的会话，当前处理中的工作保留收尾。暂停仅停止后续推进。验收通过与 Issue 关闭同步分开，汇总任务不能一键把所有子项完成。

## 界面约束

- DSH 会话只有一行标题，右侧放关联任务及原生子智能体/后台入口示意，下方是“对话 / 轨迹 / 接续”。
- 上下文与下一步集中在可拖动悬浮球中。
- 项目来源摘要归左侧，持续处理在右侧，不显示读取主机。
- 全局演示抽屉横跨左侧菜单与右侧页面，默认收起；悬浮球在其上方。
- 保留用户输入草稿；选择建议只填框，不代发送。

## 本轮检查

按用户要求没有浏览器走查。已使用 Node 检查脚本语法、页面字符串生成和关键内存状态：重复开始不多建会话；接替前当前入口不变；返回与收取分开；正式接任更新入口；自动阈值可触发接续。随后修正了来源状态待核对、重试关联作业和空结果事件的边界。

视觉布局、点击手感和信息密度仍由用户打开本原型试用反馈；这不是生产集成验收。
