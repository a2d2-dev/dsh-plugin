## 已确认方向

1. **依托 DSH。** 保留原有项目、会话、skill 使用方式，只增加 A²D² 控制面板入口。让用户逐步使用能力，避免先学一套独立管理流程。
2. **围绕用户理解的对象。** 面板以 Issue、PR、项目为主；领域身份、执行协调、Agent 和流程能力在底层提供关联与约束，不成为显眼的必经操作栏目。
3. **具体项目是上下文。** 下拉必须选择一个项目，不存在“全部项目”。“项目”页展示该项目内部的视图标签与对应数据，不展示项目目录。
4. **Issue 有独立详情。** 描述 Issue、进展与关联会话；同一 Issue 可以跨多段会话接替。区分当前处理会话、历史接续记录和评审等其他关联会话。
5. **详情布局集中。** 参考资源详情页：顶部标题与操作，概览/会话/相关工作/活动标签，全宽纵向分区。概览保留摘要，完整历史和关联内容按需展开。
6. **从三个实际痛点引入能力。** 持续从既定工作列表取得并处理 Issue；依据可配置的上下文阈值自动接续；让项目、原始 Issue、拆解工作和关联会话的实际进展可查，减少反复追问。
7. **保留 v3 的独立身份与本地能力。** 高频入口可以是 GitHub Issue，但 GitHub 不成为领域身份和完整工作闭环的必要条件。外部同步状态与工作完成事实分开。

## 下一阶段路由

依 `ask-matt`，原型分支已得到可用于开发的交互结论，应回到主流程：

`to-spec → to-tickets → implement（逐票，含 TDD 与 code-review）`

这项工作涉及真实 DSH 接入、工作记录、来源适配、会话关联与接续、持续处理，预计需要多会话实现。规格和拆票应保留本轮讨论作为依据；每张实现票自包含、声明阻塞关系，再分别执行。

第一条端到端切片优先验证“在 DSH 选择项目 → 查看 Issue → 独立详情 → 关联/进入真实会话”。它所需的最小身份与本地记录应随切片一起落地。接续、持续处理和更完整的 PR/项目协同在后续切片扩展。

不再以细节尚未穷尽为理由重开整轮概念讨论。规格阶段应通过代码核查分清现有能力与缺口；只把会影响正确性、权限或不可逆行为的未决事项单独列出。文案、密度、字段排列等可在实现时继续沟通。
