# #348 重复提醒积压修复验证

## 目的

解决 #184 会话 5 的旧定时提醒在接续时逐条重放、真实人工输入长期排队的问题，保留不同指令、作业结果和控制边界。

## 现场与根因

LF 报告 73 条排队。2026-11-01 的 journal 回放及实际页面截图核实时，队列为 72 条，其中 71 条为定时提醒，1 条为人工输入。按 schedule_id 与 reminder_prompt 比较，有 69 条重复提醒，人工消息位于第 71 位。旧提醒的 occurrence_at 属于 10 月 28 日，11 月 1 日接续时被集中搬入后继会话。

原宿主逐轮只领取一条 next-turn 输入。Task 接续完整保存原生输入后逐条投递，没有合并待处理的相同提醒；host 只在自动准入拒绝时才接回排队人工消息。自动轮次获准时，重复提醒持续消耗模型轮次，人工消息仍在尾部。

## 实现与验证步骤

在独立 worktree 基于 origin/main 实施。合并仅适用于相同 schedule_id、相同 reminder_prompt 的待处理重复 occurrence，保留最新时间的完整信封。不同指令、不同定时器、人工及未知格式消息保留；混合批次只有每项都已被较新提醒覆盖才可取消。原始 journal 不删除；Task 事件使用 discarded，不能冒称模型消费。

真实 AgentLoop/Inbox 回归先构造 69 条重复提醒及不同提醒、修改后指令和两条人工输入，确认原实现首次模型请求没有人工消息。修复后检查最新提醒和每条人工输入恰好进入模型一次，旧提醒不进入模型、不会被 sealInput 重新搬运。另覆盖持久 Task 重放、真实接续和冷恢复、模型等待中的旧队首替换、人工暂停与维护准入。

完整回归发现人工输入与接续维护请求同轮时，维护请求会被延后导致已有交接测试失败；修正须保留原维护信封及其独立准入，不以人工输入授予维护或业务额外权限。
