# A²D² 插件是方法论的载体，每个任务由主会话里的 CEO 推进

插件不再只是“A²D² 在 DSH 的一个落点”，而是 A²D² 的综合载体：方法论词汇（CONTEXT.md、ADR）、Agent 配置、技能与 DSH 侧机制放在同一个仓库里一起管版本。一个任务由一个主会话执行，主会话的 Agent 是 CEO；CEO 按 Matt 工作流推进任务，具体工作派给子代理。LF 只提供和修订原则。

## 背景

LF 管理 AI 编程时的四个痛点：

1. 看不到全局：一个项目有多少任务，每个任务现在由哪条会话在执行。
2. 会话上下文快满时要换会话，既要上下文完整，又要任务状态正确。
3. LF 只想提供和修订原则，需要一个 Agent 去推进 Matt 工作流里的具体切换。
4. Matt 工作流各步需要的智能水平不同，要按步骤选模型。

原有的 `a2d2-orchestrator` 技能把方法、LF 的原则和带日期的教训混写在一份契约里，并自带一条“派出去的一律用 Sonnet 5.5”的规定，和站点模型表（ADR 0006）各说各的。另一次梳理（会话“检查智能体团队缺失特性”）发现，DSH 实验性的智能体团队把身份、任务板和会话焊在一起，“目标”“任务”在 DSH 里各有几种互不相干的含义，于是定下“目标层 / 执行层”分层。

## 决定

- **两层词汇**：目标层是项目、任务、Agent；执行层是会话、主会话、子代理、交接、续跑条件。执行层的东西不用来定义目标层的东西。
- **任务树**：一个项目拆成多个任务，任务再拆成子任务，每个任务都是 tracker 上的一个 issue；to-tickets 切出的工单也是子任务，不另立概念。任务以 tracker 为准；插件只记 tracker 不知道的部分：每个任务的主会话与交接边。
- **子任务的两种执行方式，由 CEO 判断**：还要走 grill → to-spec → to-tickets 的子任务，由插件在同一个 workspace 里新建一个独立的根会话作为它的主会话，首条消息只给子任务 issue、父任务 issue 与 spec 的链接，父任务已定的不再问 LF；同一套规则逐层递归。已经可以直接实现的子任务，由父任务的主会话派子代理走 implement → code-review。区别只在执行层，目标层都是任务。
- **父任务靠 tracker 与通知知道子任务进展**：父任务的 CEO 每次唤醒时看子 issue 的状态；子任务验收完、关闭 issue 时，插件给父任务的主会话发一条通知把它叫醒。根会话之间没有 DSH 的子代理结束通知，这条由插件补上。
- **设计段在主会话里做**：grill → to-spec → to-tickets 由 CEO 在主会话里与 LF 完成，保持 Matt 要求的同一段不断开的上下文；每到一站切主会话自己的模型。
- **一个任务一个主会话，主会话的 Agent 是 CEO**：仿照 Paperclip 的 CEO 角色（`server/src/onboarding-assets/ceo/`）。CEO 按 Matt 工作流推进任务：该换会话时交接，该执行时派子代理。任务完成以任务验收为准。
- **主会话绑定任务 issue，并把主要问题和结论同步进去**：主会话一启动就为任务建 issue 并绑定它，to-spec 时 spec 写进同一个 issue，一个任务始终只有一个 issue。会话会换，issue 不会，所以 issue 是任务进展的持久记录，也是交接时接续内容指向的地方。正文顶部放 CEO 随时覆盖的“现状”，评论区当时间线，只记站间切换、单向门问答、决定（只链接 CONTEXT.md / ADR）、交接、子代理派发与结果五类。第一版全部由 CEO 用 `gh` 写；哪类事件常被漏记，再交给插件自动写。
- **Agent 由文件定义**：CEO 由 AGENTS.md（职责）、SOUL.md（原则）、WAKE.md（唤醒清单：去哪里取什么信息、按唤醒来源怎么处理）定义，不设 TOOLS.md；插件在主会话每次请求前现读这三份文件放进系统提示词。WAKE.md 源自 Paperclip 的 HEARTBEAT.md，改名是因为 CEO 由事件唤醒、不定时跳动，而 DSH 里 heartbeat 指网络保活。子代理以默认 Agent（不带额外配置）或特殊 Agent（为某类任务带特定上下文）的身份执行，派哪一种由 CEO 判断；特殊 Agent 定义在 `<项目>/.dsh/a2d2/agents/<名字>.md`，随项目提交，创建子代理时以 persona 交给它。
- **子代理会话的输入沿用 DSH 现有行为**：LF 直接在子代理会话里输入时，DSH 要求它的主会话已在宿主里加载；没加载时 DSH 自己会锁住输入框并提示“父会话已离线”，打开主会话即可恢复。只影响插话子代理这一种情况，主会话和子任务的根会话都不受影响，插件不额外处理。
- **子代理由插件自己创建**：插件直接调用 `ctx.subagents.startContinuable`，按站传入模型、按 Agent 传入 persona，不依赖实验性的智能体团队。子代理结束时 DSH 会自动通知父会话，CEO 由此被唤醒。第一版只靠事件唤醒，不设定时兜底：A²D² 现在没用 DSH 的定时提醒，不为它新加机制；子代理卡住时由插件已有的「现状」区块（疑似卡住）让 LF 看见。
- **原则在 SOUL，不在技能**：SOUL 由 LF 维护。CEO 的 SOUL 分全局（`~/.dsh/a2d2/SOUL.md`）与项目（`<项目>/.dsh/a2d2/SOUL.md`，随项目提交）两层，项目层优先。AGENTS.md 与 WAKE.md 属于方法，随插件发布。
- **单向门 / 双向门**：双向门（可撤回）由 CEO 自决、事后同步；单向门（生产、删数据、对外发布、范围变更）用结构化提问交给 LF 并等待。原技能里关于“不可逆怎么判”“严格程度随阶段调”的教训，压缩成这一条原则写进 SOUL。
- **按 Matt 步骤选模型**：站点模型表是唯一标准，可配置。执行者就是 implement 站，评审者就是 code-review 站；“一律 Sonnet 5.5”变成这两站的候选值。模型跟站走，不写进 SOUL。
- **交接时主会话分两步换人**：准备交接时任务标为“交接中”，后继 take 时才接任主会话；接续内容里的任务状态只写 tracker 指针，不写摘要。
- **只在 DSH 上跑 CEO**：Claude Code 没有插件，现有 `a2d2-orchestrator` 技能冻结、不再更新；不维护第二份纯文字的 CEO。
- **芯片不代发送只管人点的芯片**：ADR 0003、0005 的“永不代发送”继续适用于 LF 点的芯片；CEO 推进的站间切换不经过芯片。

## 被否方案

- **单独的推进会话，不做阶段内的活**：多了一种会话，LF 要在推进会话和干活的会话之间来回切；主会话本身按 Matt 相位边界换会话，上下文撑满的问题由交接解决。
- **插件后台按固定规则推进、不调用模型**：站间切换要判断“这一阶段做完没有”，规则写不出来。
- **用实验性的智能体团队承载子代理**：队友只能继承队长的模型，没法按站选；身份、任务板焊在队长会话上，一交接就丢；界面上队友和子代理是两个入口。
- **插件自己存一份任务清单**：成了第二个 tracker，两边迟早对不上。
- **按角色选模型（执行者一个、评审者一个）**：和按站选是两套标准；角色本来就落在站上。
- **CEO 用 DSH 的 `/goal` 持续推进**：续跑驱动在会话一空闲就再推一轮，而 CEO 派出子代理后自己就是空闲的，结果是等待期间反复空推、每轮重发整段历史、耗尽轮数或连续三轮同样受阻后被停掉，等于轮询。CEO 的每个动作都有事件唤醒，用不上它；以后出现 CEO 需要连续自己干活的场景再评估。
- **把插件原来的“任务”改名为“目标”**：和 DSH 的 Goal（续跑条件）撞名，而 LF 的说法本来就是“项目 → 任务”。

## 后果

- `a2d2-orchestrator` 技能会被拆掉：角色分工与执行契约提炼进 CEO 的 AGENTS.md 和 WAKE.md，原则进 SOUL.md，派单模板保留为 WAKE.md 引用的参考资料。下一步咨询里读这个技能描述、多给一颗编排芯片的逻辑（`src/consult.ts`）要跟着改。
- 插件的任务文档要从“会话的聚合”改成“任务的执行记录”：记主会话与交接边，并能指向 tracker 上的任务与子任务。
- 子任务关闭时通知父任务主会话，需要插件把子任务 issue 的关闭和父任务主会话对应起来。
