# 工作事实以主存为准；现阶段 GitHub 为主存，本地为缓存

**状态：当前目标决策。** 任务记录与验收事实保存在项目选定的主存。现阶段主存是云端 GitHub：Task 记录为 Issue，子任务记录为原生 sub-issue；本地工作库是缓存与执行协调状态，不是权威。纯本地主存是尚未启用的候选模式，启用需要单独的阶段决策与迁移。

## 决定

- **主存可选，权威跟随主存。** 项目选定主存后，只有主存里的记录能作为任务树、规格、验收、证据与完成的依据；缓存与主存冲突时以主存为准。现阶段所有项目都使用云端 GitHub。
- **现阶段每个 Task 对应一个 Issue，子任务对应一个原生 sub-issue。** 不得在主存之外创建没有记录对应物的 Task 或子任务；只在本地出现的工作项按无效缓存处理，不能用于完成门、验收或执行授权。
- **本地工作库是缓存。** 它保存主存记录的投影，也保存本机的执行协调事实。缓存缺失不等于主存没有；缓存可以过期，重建以主存记录为输入。
- **执行协调事实由本机权威。** TaskExecution、owner 与代次、当前处理会话、作业和事件收件箱是运行时事实。它们不写入主存，也不改变任务记录与验收的权威位置。
- **两类写操作分开。** 业务写走主存（`gh`/同步适配器，使用稳定操作身份与恢复点，待发布、成功、失败、冲突和结果未知必须可区分）；执行协调写走本机。不得把本地缓存写入当成业务写完成。
- **完成必须发布成功后才成立。** 发布前本地只保存「待发布」意图并显示为完成待同步；主存不可用时该 Task 无法收口，而不是另有一份本地完成事实。
- **外部观察只是候选事实。** Issue 状态、原生 sub-issue 范围、PR 与评论要校验来源、版本、权限和当前完成状态后才能进入缓存或主存；外部负责人、标签、评论不授予执行权。
- **一个外部对象在同一记录范围内只对应一个领域对象。** 重复发现和导入复用原记录，不得复制正在执行的工作。
- **拆子工作先过立项判断。** 只有同时具备独立目标、独立验收、独立生命周期、需独立授权和独立交付物的块才成为子任务；其余留在父任务内作为需求块，由本会话执行或委派。现阶段子任务必须以 sub-issue 创建，不得由本地记录凭空产生。
- **启用纯本地主存是显式阶段决策。** 需要一次性迁移、稳定映射与执行资格处理；迁移完成前不得混用两套权威。

## 数据与一致性边界

主存写入与执行协调写入各有事务边界；跨系统步骤使用稳定操作身份与恢复点，不承诺全局原子提交或外部副作用恰好一次。GitHub 自身状态以远端为准；本地缓存与主存之间的发布/观察使用同一组操作身份和恢复点。不能把 GitHub 评论更新当作数据库 CAS，也不能把本地缓存写入当作主存写入。

## 场景

- **现阶段接入一个 Issue**：读取 Issue → 建立 Task 缓存与执行协调记录 → 用户显式开始 → 执行 → 证据写回 Issue → 完成发布成功 → 可选关闭。
- **要拆子工作**：先过立项判断。是子任务则创建 sub-issue（原生父子关系），本地记录作为投影；不是则留在父任务内做需求块与委派。
- **GitHub 不可用**：读取最后已知缓存并标注新鲜度；业务写排队为待发布；完成在发布成功前不成立。
- **本地缓存出现主存没有的子任务记录**：不是必要子项，不能阻断父任务完成；按无效记录清理或忽略。
- **子 issue 被关闭或重开**：关闭是外部观察，不自动等于通过验收；重开观察不自动重跑已验收工作，完成仍以主存记录为准。
- **未来纯本地主存**：另立阶段决策并完成迁移；迁移前本地记录仍不是权威。

## 被否方案

- **本地恒为主存，GitHub 只做可选协同**：与现阶段「GitHub 是唯一数据源」的部署事实冲突，会把缓存记录抬成业务身份，出现本地创建、没有 sub-issue 对应的「子任务」。
- **两套主存并行、冲突时各自为准**：没有统一仲裁，完成与门禁会互相矛盾。

## 实现覆盖

业务写主存、缓存投影、执行协调记录分域，以及子任务必须由 sub-issue 产生，是本次目标；现有本地工作库同时承载业务事实与执行协调，需要按本决策拆分并为既有本地子任务记录提供迁移/清理路径。
