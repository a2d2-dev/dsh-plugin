# 每条知识只放在一处：规则在技能，结构在插件，原则在 SOUL

一条知识一旦有两份，迟早会漂移。所以每条知识只放在一处：工作流的规则放在技能里，展示结构放在插件里，原则放在 SOUL 里，决定放在 CONTEXT.md 和 ADR 里。其他地方只引用，不复述。

## 决定

- **模型指令 = 技能原文 + 纯参数信封**：
  - 插件的两段模型指令（交接指令、下一步咨询）都按这个方式组装。
  - 信封里不出现任何技能已有的规则；技能里也不出现文件路径、JSON 形状这类调用参数。
  - 技能和插件的场景冲突时，直接改技能文件，让它对所有调用方都成立，不在信封里加纠正。
  - 注入范围：技能正文相对引用的本地 markdown 都按原文注入，不硬编码文件名。
- **技能缺失时不内嵌回落**：结果里标注「未读到 skill」，模型凭自身判断执行。降级必须让人看得见。
- **插件拥有结构，不拥有规则**：
  - 公路图的阶段与区枚举、匝道并入点，由插件以数据维护。
  - 什么时候去哪个阶段、走法怎么选，只来自 ask-matt 原文。
  - 主干、服务区、匝道、路基是闭集，独立区是开集。
  - 「已过的阶段」由客户端按主干顺序推导，不由模型报告。
- **原则与方法分开**：
  - 原则只写在 SOUL.md 里，由 LF 写。
  - 方法只写在随插件发布的 AGENTS.md、WAKE.md 和技能里。
  - SOUL 不放方法，也不放模型。
  - 教训要么改写成原则进 SOUL，要么写成 ADR。
- **决定只记一处**：决定写在 CONTEXT.md 或 ADR 里，issue 时间线只放链接、不复制。

## 被否方案

- **插件内嵌技能规则的精简版或改写版**：会和真源漂移。
- **技能只读，由信封纠正**：纠正句本身就是一份影子拷贝。
- **当前位置用自由文本**：既没法画成图，也没法校验，模型答偏了也不会报错。
- **运行时从 ask-matt 原文解析结构**：原文是写给人读的散文，解析很脆弱；而结构的变化远比措辞少。
- **方法、原则和教训混写在一份契约里**：也就是 `a2d2-orchestrator` 的做法。修订原则时会碰到方法，反过来也一样。

## 后果

- 技能一改进，交接和咨询自动跟着变好，插件代码不用动。
- ask-matt 的主干一改名，咨询就会显式报错，直到插件的枚举同步更新。这是有意接受的耦合。
