# 阶段的 Agent 决定它在哪里执行；一条会话只跑一个 Agent

每个阶段指定一个 Agent。指定 CEO 的阶段在主会话里执行，指定工程师或评审的阶段派子代理执行。一条会话从头到尾只以一个 Agent 的身份运行，要换 Agent 就换会话。

## 决定

- **执行位置跟着 Agent 走**：
  - 阶段 Agent 表（ADR 0009）为每个阶段指定 CEO、工程师或评审三者之一。
  - 指定 CEO 的阶段在主会话里执行。
  - 指定工程师或评审的阶段派子代理执行。
- **选 Agent 的判据：这个阶段需不需要人参与。** 需要人参与的指定 CEO，因为 DSH 子代理是非交互的（审批固定为 never），没法问 LF。出厂指定如下：

  | 阶段 | Agent |
  |---|---|
  | implement | 工程师 |
  | code-review | 评审 |
  | 其余全部：grill、to-spec、to-tickets、triage、wayfinder、improve-codebase-architecture、domain-modeling、codebase-design、prototype、diagnosing-bugs、handoff | CEO |

  因此设计阶段都在主会话里连续完成，保持同一段上下文。
- **会话的 Agent**：

  | 会话 | Agent |
  |---|---|
  | 主会话 | CEO |
  | 子代理 | 派发时按阶段取得的 Agent |
  | 芯片新建的会话 | 芯片上写明的 Agent（ADR 0007） |
  | 其他会话（LF 自己开的、没绑定任务的） | 没有 Agent |

- **一条会话只跑一个 Agent**：
  - 阶段没做完时，只能 continue 或派子代理。
  - 跨阶段时，下一阶段的 Agent 与本会话的 Agent 相同，才能 continue。不同、或本会话没有 Agent 时，就开新会话（clear、handoff、compact）或派子代理，并在创建时定好 Agent。
  - 不在会话中途换模型。
- **子任务的两种执行方式，由 CEO 判断**：
  - **还要走设计阶段的子任务**：插件在同一个 workspace 里新建一个根会话，作为它的主会话（`open_subtask`）。首条消息只给子任务 issue、父任务 issue 与 spec 的链接；父任务已定的事不再问 LF。同一套规则逐层递归。
  - **已经可以直接实现的子任务**：由父任务的主会话派子代理，走 implement → code-review。
- **子代理由插件直接创建**：插件调用 `ctx.subagents.startContinuable`，按阶段的 Agent 传入模型与配置。
- **CEO 只由事件唤醒**：
  - 唤醒来源有四种：子代理结束的 DSH 通知、子任务关闭的插件通知、所关注 PR 的状态变化、LF 的消息。
  - 不用 `/goal`，不设定时兜底。
  - 子代理卡住时，由「现状」区块的「疑似卡住」让 LF 看见。
- **LF 在子代理会话里插话**：沿用 DSH 现有行为。主会话没有加载时，输入框锁住并提示「父会话已离线」，打开主会话即可恢复。

## 被否方案

- **允许一条会话分段换 Agent**：会话的定义要变成「一串 Agent 段」，面板、交接、装配都得按段处理，换来的只是少开一次会话。
- **单独开一条推进会话，自己不干阶段内的活**：多了一种会话，LF 要在推进会话和干活的会话之间来回切。
- **插件在后台按固定规则推进、不调用模型**：判断「这个阶段做完没有」的规则写不出来。
- **CEO 用 `/goal` 持续推进**：CEO 派出子代理后自己就空闲了。续跑会在等待期间反复空推，每轮重发整段历史，最后耗尽轮数或被判受阻，等于轮询。
